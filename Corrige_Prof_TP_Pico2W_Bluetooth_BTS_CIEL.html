Corrigé Partie 1 : Passerelle Série, Commandes AT & Mesures UART

✅ Question 1.0 (Analyse de code) : Explication du programme double série passerelle

1. Architecture du pontage bidirectionnel :

  • Serial correspond au port virtuel USB connecté à l'ordinateur du développeur (PC à 115200 bauds).
  • BT_SERIAL (défini sur Serial2) correspond au contrôleur matériel UART1 du RP2350 relié au module Grove Bluetooth (sur GP4/TX et GP5/RX à 9600 bauds).

2. Rôle des boucles dans loop() :

  • while (Serial.available() > 0) : Vérifie s'il y a des octets en attente dans le tampon FIFO de réception USB du PC. Si oui, chaque caractère est lu par Serial.read() et immédiatement réémis sur l'UART physique du Bluetooth par BT_SERIAL.write(c). C'est le sens PC → Bluetooth (transmission des commandes AT ou des données saisies au clavier PC).
  • while (BT_SERIAL.available() > 0) : Vérifie s'il y a des octets reçus par la broche GP5 depuis le Bluetooth. Si oui, chaque caractère est lu par BT_SERIAL.read() et retransmis vers l'écran de l'ordinateur par Serial.write(c). C'est le sens Bluetooth → PC (affichage des réponses OK, des statuts ou des données reçues par radio).

3. Pourquoi le programme est-il transparent et non-bloquant ?
Le code n'utilise aucune fonction d'attente bloquante (aucun delay(), aucun while(!Serial.available())). Si aucun octet n'est disponible, le processeur passe immédiatement à l'instruction suivante. La boucle loop() s'exécute à très haute fréquence (plusieurs centaines de milliers de passes par seconde sur le Cortex-M33 à 150 MHz), assurant un pontage quasi instantané avec une latence inférieure à la microseconde.

✅ Question 1.1 : Adresse matérielle Bluetooth (BD_ADDR) vs Adresse MAC Ethernet

• Format de la BD_ADDR relevée : Ex : 00:1B:10:25:A3:8F (48 bits / 6 octets, souvent affiché sans deux-points 001B1025A38F dans la réponse AT).

• Comparaison avec l'adresse MAC Ethernet (IEEE 802.3) :
La structure est rigoureusement identique :

  • Les 3 premiers octets (24 bits de poids fort) constituent l'OUI (Organizationally Unique Identifier), assigné par l'IEEE au fabricant du chipset radio (ex: Texas Instruments, Cambridge Silicon Radio, Qualcomm).
  • Les 3 derniers octets (24 bits de poids faible) forment le NAP/LAP (Network/Lower Address Part), identifiant unique du circuit intégré gravé en usine.
Comme pour Ethernet, cette adresse garantit l'unicité globale de l'interface réseau sur la couche liaison de données (Couche 2 OSI).

✅ Question 1.2 : Mesure temporelle du temps bit (Tbit) et calcul d'écart relatif

• Calcul théorique :

Tbit_th = 19600 = 0,000104167 s = 104,17 µs

• Mesure expérimentale aux curseurs WaveForms (ΔX) : Valeur typique mesurée entre 104,1 µs et 104,3 µs.

• Calcul d'erreur relative (Exemple avec 104,2 µs mesuré) :

Écart (%) = | 104,20 − 104,17 | 104,17 × 100 = 0,03 %

Conclusion technique : L'erreur est largement inférieure au seuil limite de ±2 % toléré par les oscillateurs UART asynchrones. La synchronisation sur le bit de Start ne risque donc aucun décalage d'échantillonnage sur les 8 bits de données.

✅ Question 1.3 : Mesure analogique Scope (Scope 1+) & Tolérance LVTTL 3,3V

• Niveau haut VOH mesuré : 3,28 V à 3,32 V.

• Temps de montée tr (10% → 90%) : ~18 ns à 35 ns (selon la capacité parasite du câble Grove et de la sonde MTE).

• Conformité : Parfaitement conforme aux spécifications LVTTL 3,3V du microcontrôleur RP2350 ($V_{IH\_min} = 2,0\ \text{V}$ et $V_{OH\_min} = 2,4\ \text{V}$). Aucun dépassement excessif (overshoot) susceptible d'endommager les diodes de clamping des broches GPIO.

Corrigé Partie 2 : Profil SPP, I²C & Buffer Circulaire

✅ Approfondissement : Pile SPP / RFCOMM / L2CAP & Buffer Circulaire

1. Pourquoi cette pile protocolaire ?
Le profil SPP crée un canal de télécommunication série au-dessus des couches radio. L2CAP découpe les blocs et gère la qualité de service, tandis que RFCOMM fournit le flux d'octets avec émulation de ports de communication (signaux virtuels RX, TX, ACK). Les PC sous Windows voient un port COMx sortant classique, utilisable directement avec n'importe quel logiciel de terminal série.

2. Code C++ de réception non-bloquante avec Buffer Circulaire (Ring Buffer FIFO) :

#include <Wire.h>
#include <Adafruit_GFX.h>
#include <Adafruit_SSD1306.h>

#define SCREEN_WIDTH 128
#define SCREEN_HEIGHT 64
Adafruit_SSD1306 display(SCREEN_WIDTH, SCREEN_HEIGHT, &Wire, -1);

#define BT_SERIAL Serial2
#define RING_BUF_SIZE 128

// Tampon circulaire
uint8_t ringBuffer[RING_BUF_SIZE];
volatile uint8_t head = 0;
uint8_t tail = 0;

void setup() {
  Serial.begin(115200);
  
  BT_SERIAL.setTX(4);
  BT_SERIAL.setRX(5);
  BT_SERIAL.begin(9600);

  Wire.setSDA(8);
  Wire.setSCL(9);
  Wire.begin();

  display.begin(SSD1306_SWITCHCAPVCC, 0x3C);
  display.clearDisplay();
  display.setTextSize(1);
  display.setTextColor(SSD1306_WHITE);
  display.setCursor(0, 0);
  display.println(F("PUPITRE BT PRET"));
  display.display();
}

void loop() {
  // 1. Acquisition en arrière-plan sans bloquer
  while (BT_SERIAL.available() > 0) {
    uint8_t c = BT_SERIAL.read();
    uint8_t nextHead = (head + 1) % RING_BUF_SIZE;
    if (nextHead != tail) { // Évite l'écrasement en cas de saturation
      ringBuffer[head] = c;
      head = nextHead;
    }
  }

  // 2. Traitement des données prêtes dans le tampon
  if (head != tail) {
    char msg[64];
    uint8_t idx = 0;
    while (head != tail && idx < 63) {
      char c = (char)ringBuffer[tail];
      tail = (tail + 1) % RING_BUF_SIZE;
      if (c == '\n' || c == '\r') break;
      msg[idx++] = c;
    }
    msg[idx] = '\0';

    if (idx > 0) {
      // Affichage OLED
      display.clearDisplay();
      display.setCursor(0, 0);
      display.println(F("MSG RECU :"));
      display.setCursor(0, 20);
      display.println(msg);
      display.display();

      // Envoi de l'accusé de réception (ACK)
      BT_SERIAL.print(F("ACK: "));
      BT_SERIAL.println(msg);
    }
  }
}
✅ Question 2.1 : Décodage I²C & Fréquence d'horloge SCL

• Fréquence SCL mesurée : 100 kHz (période $T_{SCL} = 10\ \mu\text{s}$).

• Mode de fonctionnement : Standard-mode (Sm), caractérisé par un débit nominal de 100 kbit/s. La forme des fronts montants présente une allure exponentielle typique liée à la charge RC ($R_{pull-up} \approx 4,7\ \text{k}\Omega$ et capacité parasite des pistes/câbles Grove $\approx 50\ \text{pF}$).

Corrigé Partie 3 : Clavier Série (UART0), Matrice & Accéléromètre 3 Axes

✅ Question 3.1 : Adressage matériel sur bus I²C partagé

• Principe de multiplexage par adresse :
Sur le bus I²C partagé, les lignes physiques SDA et SCL sont communes à tous les périphériques. Le maître (Pico 2 W) débute chaque transaction par une condition de START suivie d'un octet d'adresse (7 bits d'adresse + 1 bit R/W). Seul le périphérique dont l'adresse interne correspond génère un accusé de réception (ACK) en forçant la ligne SDA au niveau bas au 9e coup d'horloge SCL. Tous les autres circuits restent en haute impédance.

• Adresses physiques relevées lors du scan I²C :

  • 0x3C : Afficheur graphique OLED SSD1306.
  • 0x53 : Capteur d'accélération 3 axes numérique (ADXL345 / LIS3DHTR).
  • 0x70 : Matrice de LED 8x8 (contrôleur Holtek HT16K33).

• Gestion conjointe du Clavier Série sur UART0 :
Le clavier numérique série émet ses caractères en asynchrone sur UART0 (GP1/RX Pico) à 9600 bauds. Il est lu indépendamment via Serial1 sans aucune collision possible avec le bus I²C ni avec le Bluetooth (sur UART1/Serial2).

Corrigé Partie 4 : Machine à États Finis (FSM) & Checksum XOR

✅ Question 4.1 : Démonstration mathématique du Checksum XOR (LRC)

Trame à valider : ID=0x01, CMD=0x20, LEN=0x01, DATA=0x41 ('A').

Calcul binaire étape par étape bit à bit (OU Exclusif : $0 \oplus 0 = 0$, $1 \oplus 1 = 0$, $0 \oplus 1 = 1$) :

  Octet 1 (ID)   : 0000 0001 (0x01)
^ Octet 2 (CMD)  : 0010 0000 (0x20)
------------------------------------
= Résultat int.1 : 0010 0001 (0x21)

^ Octet 3 (LEN)  : 0000 0001 (0x01)
------------------------------------
= Résultat int.2 : 0010 0000 (0x20)

^ Octet 4 (DATA) : 0100 0001 (0x41)
------------------------------------
= Checksum final : 0110 0001 (0x61 = caractère ASCII 'a')

Le Checksum attendu est donc 0x61 (valeur décimale 97).

Code complet de l'automate FSM et du contrôle d'intégrité :

uint8_t calculerChecksum(const uint8_t* buffer, uint8_t longueur) {
  uint8_t ck = 0x00;
  for (uint8_t i = 0; i < longueur; i++) {
    ck ^= buffer[i];
  }
  return ck;
}

enum FSM_State { WAIT_START, READ_HEADER, READ_PAYLOAD, VERIF_CHECKSUM };
FSM_State etatFSM = WAIT_START;

uint8_t rxBuffer[32];
uint8_t rxIndex = 0;
uint8_t payloadLen = 0;
uint8_t checksumRecu = 0;

void traiterOctet(uint8_t c) {
  switch (etatFSM) {
    case WAIT_START:
      if (c == '$') {
        rxIndex = 0;
        etatFSM = READ_HEADER;
      }
      break;

    case READ_HEADER:
      rxBuffer[rxIndex++] = c;
      if (rxIndex == 3) { // ID, CMD, LEN
        payloadLen = rxBuffer[2];
        etatFSM = (payloadLen > 0) ? READ_PAYLOAD : VERIF_CHECKSUM;
      }
      break;

    case READ_PAYLOAD:
      rxBuffer[rxIndex++] = c;
      if (rxIndex == 3 + payloadLen) {
        etatFSM = VERIF_CHECKSUM;
      }
      break;

    case VERIF_CHECKSUM:
      if (rxIndex == 3 + payloadLen) {
        checksumRecu = c;
        rxIndex++;
      } else if (c == '#') { // Délimiteur de fin reçu
        uint8_t ckCalcule = calculerChecksum(rxBuffer, 3 + payloadLen);
        if (ckCalcule == checksumRecu) {
          // Trame intègre : exécution de la commande
          BT_SERIAL.println(F("ACK_FRAME_VALID"));
          executerCommande(rxBuffer[1], &rxBuffer[3], payloadLen);
        } else {
          // Erreur d'intégrité détectée
          BT_SERIAL.println(F("NACK_CHECKSUM_ERROR"));
        }
        etatFSM = WAIT_START;
      } else {
        etatFSM = WAIT_START; // Erreur de trame
      }
      break;
  }
}

Corrigé Partie 5 : Débit sur 10 000 octets & Bluetooth Interne CYW43439

✅ Mesure de Débit sur 10 000 octets & Rendement utile

• Calcul de la durée théorique de transmission :
À 9600 bauds avec le format 8N1 (1 bit start, 8 bits data, 1 bit stop = 10 bits transmis par octet utile) :

Duréeth = 10 000 octets × 10 bits9600 bauds = 10,417 s = 10 417 ms

• Débit utile théorique :

Dutile_th = 10 000 × 8 bits10,417 s = 7680 bit/s = 7,68 kbit/s

• Rendement utile du protocole physique :

Rendement = 8 bits utiles10 bits physiques = 80 %

Note d'évaluation : Les étudiants relèvent en pratique une durée d'environ 10,5 à 10,8 secondes, due à la légère gigue logicielle et aux accusés radio Bluetooth.

✅ Question 5.1 : Comparatif Bluetooth Externe UART vs Interne CYW43439

Synthèse comparative :

  • Avantages du module externe Grove UART :
    • Décharge complète du processeur hôte (la pile radio Bluetooth tourne sur le microcontrôleur dédié du module).
    • Empreinte mémoire Flash/RAM négligeable sur le Pico (économie de plus de 60 Ko de RAM).
    • Simplicité de développement (manipulation de simples flux d'octets UART).
    • Certification radio simplifiée (module pré-certifié CE/FCC).
  • Avantages du Bluetooth interne CYW43439 :
    • Coût unitaire (BOM) nettement inférieur : aucun circuit imprimé additionnel requis.
    • Compacité physique optimale pour l'intégration dans un boîtier étanche scellé.
    • Débits radio bien plus élevés (jusqu'à 1 à 2 Mbit/s en BLE 5.2).

Préconisation industrielle : Pour un capteur autonome ultra-basse consommation sur batterie, la solution interne BLE (CYW43439) est préconisée car elle permet de basculer en mode veille profonde (Deep Sleep) entre deux émissions d'annonces (Advertising), alors qu'un module externe sous tension consomme en continu 8 à 15 mA.

✅ Question 5.2 : Synthèse Cybersécurité (Bluetooth SPP vs TLS)

1. Deux vulnérabilités majeures de la solution Bluetooth SPP déployée :

  1. Faiblesse du PIN fixe à 4 chiffres (Authentification faible) : L'espace des clés est restreint à $10^4 = 10\ 000$ combinaisons possibles. Une attaque par force brute ou écoute passive de l'échange de clés (E0 stream cipher) permet de casser le secret en quelques secondes.
  2. Absence de chiffrement et d'authentification applicative : Les octets circulent en clair au-dessus du canal RFCOMM. Contrairement à TLS qui authentifie le serveur via des certificats X.509 et chiffre les données en AES-GCM avec Perfect Forward Secrecy, le lien SPP est vulnérable aux attaques de type Man-in-the-Middle (MitM) et aux écoutes clandestines passives.

2. Deux mesures de remédiation conformes ANSSI :

  1. Activer le mode Bluetooth Secure Connections (SSP) avec association par code numérique dynamique (Numeric Comparison) ou clé pré-partagée longue (PSK ≥ 128 bits).
  2. Sur-chiffrer la charge utile applicative avec un protocole de chiffrement authentifié moderne (ex : ChaCha20-Poly1305 ou AES-128-CCM) avec clés éphémères négociées par échange Diffie-Hellman sur courbes elliptiques (ECDH).
