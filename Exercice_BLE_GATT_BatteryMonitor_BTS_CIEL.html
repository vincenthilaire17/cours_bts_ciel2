Contexte Industriel & Principe du Mode BLE Connecté (GAP / GATT)

Un équipement mobile d'atelier embarque une carte Arduino Nano 33 BLE (SoC Nordic nRF52840, logique 3,3 V) chargée de surveiller en temps réel le niveau de charge de sa batterie via son entrée analogique A0 et de le transmettre à la tablette d'un technicien (application nRF Connect ou LightBlue).

Architecture GATT (Generic Attribute Profile) : En BLE connecté, le périphérique joue le rôle de Serveur GATT et organise ses données de manière hiérarchique en déclarant un ou plusieurs Services (regroupement fonctionnel identifié par un UUID, ex. 0x180F pour la batterie), chacun contenant une ou plusieurs Caractéristiques (les variables/données élémentaires avec leurs droits d'accès Read, Write ou Notify, identifiées par un UUID, ex. 0x2A19 pour le niveau en %).

Principe de fonctionnement en 2 phases :

  1. Phase d'Advertising (en attente de connexion) : Le périphérique (Peripheral) diffuse périodiquement des trames d'annonce connectables (ADV_IND) sur les 3 canaux radio d'Advertising (37, 38, 39) contenant son nom ("BatteryMonitor") et l'UUID de son service standard (0x180F).
  2. Phase Connectée (Serveur GATT) : Dès qu'un appareil Central (tablette/smartphone) détecte l'annonce, il envoie une trame CONNECT_IND qui ouvre une liaison point-à-point sur les 37 canaux de données. Le Peripheral stoppe alors son Advertising et pousse les valeurs de batterie au Central via des Notifications GATT (BLENotify).
Point Cybersécurité : Connexion Ouverte sans Code PIN ni Identification

Dans l'implémentation de base utilisant ArduinoBLE ci-dessous, aucune permission de sécurité n'est imposée sur les caractéristiques GATT : le périphérique opère en BLE Security Mode 1, Level 1 (No authentication, no encryption). N'importe quel Central à portée peut se connecter sans code PIN ni identification, lire les données en clair et monopoliser la connexion unique du capteur.

Partie 1 : Analyse du Firmware « Battery Monitor » (ArduinoBLE) 6,5 points • ~25 min

Le code source Arduino/C++ ci-dessous a été volontairement allégé de ses commentaires explicatifs, remplacés par des repères numérotés [1] à [7].

#include <ArduinoBLE.h>

BLEService batteryService("180F");                                         [1]
BLEUnsignedCharCharacteristic batteryLevelChar("2A19", BLERead | BLENotify);

int oldBatteryLevel = 0;
long previousMillis = 0;

void setup() {
  Serial.begin(9600);
  while (!Serial);
  pinMode(LED_BUILTIN, OUTPUT);

  if (!BLE.begin()) {                                                      [2]
    Serial.println("starting Bluetooth® Low Energy module failed!");
    while (1);
  }

  BLE.setLocalName("BatteryMonitor");                                      [3]
  BLE.setAdvertisedService(batteryService);
  batteryService.addCharacteristic(batteryLevelChar);
  BLE.addService(batteryService);
  batteryLevelChar.writeValue(oldBatteryLevel);

  BLE.advertise();                                                         [4]
  Serial.println("Bluetooth® device active, waiting for connections...");
}

void loop() {
  BLEDevice central = BLE.central();                                       [5]

  if (central) {
    Serial.print("Connected to central: ");
    Serial.println(central.address());
    digitalWrite(LED_BUILTIN, HIGH);

    while (central.connected()) {                                          [6]
      long currentMillis = millis();
      if (currentMillis - previousMillis >= 200) {
        previousMillis = currentMillis;
        updateBatteryLevel();
      }
    }
    digitalWrite(LED_BUILTIN, LOW);
    Serial.print("Disconnected from central: ");
    Serial.println(central.address());
  }
}

void updateBatteryLevel() {                                                [7]
  int battery = analogRead(A0);
  int batteryLevel = map(battery, 0, 1023, 0, 100);

  if (batteryLevel != oldBatteryLevel) {
    Serial.print("Battery Level % is now: ");
    Serial.println(batteryLevel);
    batteryLevelChar.writeValue(batteryLevel);
    oldBatteryLevel = batteryLevel;
  }
}

Partie 2 : Relevé d'Autonomie en Phase d'Advertising (Digilent AD3) 6,5 points • ~30 min

La majeure partie du temps, aucun technicien n'est connecté au capteur : le module BLE (SoC nRF52840 autonome, LED éteinte) reste donc en phase d'Advertising connectable (ADV_IND) en attente d'un Central, alimenté par une pile bouton lithium CR2032 (3,0 V, capacité nominale Cnom = 225 mAh, facteur d'efficacité η = 0,80).

L'intervalle d'Advertising est réglé à Tcycle = 1,0 s (1 000 ms). La Figure 1 présente le relevé fictif de la tension ΔU aux bornes d'un shunt Rshunt = 10 Ω capturé à l'oscilloscope Digilent Analog Discovery 3 sur un cycle complet d'Advertising.

Partie 3 : Décodage d'une Trame BLE Connectée (Notification GATT) & CRC 7 points • ~30 min

Un technicien connecte maintenant sa tablette (Central) au périphérique "BatteryMonitor" et s'abonne aux notifications de la caractéristique Battery Level (0x2A19). Lorsque la tension sur A0 varie, la carte exécute batteryLevelChar.writeValue(batteryLevel) et émet une trame BLE de données (Data Channel Packet) transportant une Notification GATT (ATT Handle Value Notification).

La Figure 2 détaille la structure normalisée de cette trame de 18 octets (encapsulation Link Layer → L2CAP → ATT/GATT).
