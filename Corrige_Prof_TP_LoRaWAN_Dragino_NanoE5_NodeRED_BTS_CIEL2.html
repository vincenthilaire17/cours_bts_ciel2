🛠️ Préparation enseignant avant la séance (≈ 45 min la première fois)
  1. Serveur réseau LoRaWAN (ChirpStack v4) sur un PC / VM du lycée (dépôt officiel chirpstack-docker : ChirpStack + gateway-bridge UDP 1700 + broker Mosquitto + PostgreSQL + Redis). Activer la région eu868. Ports ouverts sur le PC serveur : 8080/tcp (interface), 1700/udp (passerelle), 1883/tcp (MQTT, accessible aux PC élèves).
  2. Profil d'équipement (Device profile) : région EU868, LoRaWAN 1.0.3, Regional parameters revision A, classe A, OTAA, Uplink interval 60 s. Créer une Application (ex. lycee-lora) avec l'intégration MQTT activée (par défaut dans ChirpStack v4).
  3. Fiche de la salle : une AppKey de 32 caractères hexadécimaux par binôme (générée aléatoirement), les adresses IP, comptes, nom des équipements (groupe-1, groupe-2…).
  4. Passerelle Dragino LPS8v3 (EU868, EC25) : la mettre à jour si besoin, noter son IP (DHCP ou réseau Wi-Fi propre dragino-xxxxxx, mot de passe usine de la gamme Dragino : dragino+dragino, compte root). Remplacer le mot de passe usine. Pré-déclarer la passerelle dans ChirpStack avec son Gateway EUI (ou faire faire cette étape par le binôme rapporteur).
  5. Câble de mesure (1 ou 2 pour la classe) : câble USB-A/mini-USB dont le fil rouge (+5 V) est coupé et rebouclé par une résistance de 1,1 Ω du TI myParts Kit, fils de reprise de part et d'autre pour les pointes de l'AD3 (isoler soigneusement).
  6. Postes élèves : Arduino IDE (carte « Arduino Nano », processeur ATmega328P — Old Bootloader pour les clones), Node-RED + node-red-dashboard, dossier C:/LoRa créé (ou laisser Node-RED le créer).
  7. Test préalable obligatoire : faire joindre un nœud de test, vérifier l'événement up dans ChirpStack et la réception dans Node-RED.
⚠️ Points de vigilance en séance (retours d'expérience probables)
  1. Pas de réponse à AT : (a) fin de ligne du moniteur série ≠ « NL et CR » ; (b) RX/TX inversés → essayer SoftwareSerial lora(3, 2) ; (c) module sur un autre connecteur Grove que D2 (adapter les numéros) ; (d) alimentation USB insuffisante.
  2. Le JOIN échoue (Join failed) : DevEUI mal recopié dans ChirpStack, AppKey différente, profil non EU868, passerelle absente ou hors ligne, nœud trop loin / antenne oubliée. Dans ChirpStack, l'onglet LoRaWAN frames de la passerelle montre si la demande de join est reçue (si elle l'est mais qu'aucune réponse n'est émise : clé erronée).
  3. Plusieurs binômes, une seule passerelle : chaque équipement a son DevEUI propre (pas de conflit). Vérifier que chaque groupe a bien renseigné MON_DEVICE dans Node-RED, sinon les graphes mélangent les nœuds.
  4. Duty cycle : tolérer 60 s minimum entre trames ; en SF12 la période de 60 s est inférieure à l'intervalle mini théorique de 132 s pour un canal, mais le nœud répartit ses trames sur plusieurs canaux ; faire constater et discuter (limite réglementaire par sous-bande).
  5. Powerbank qui s'éteint : courant trop faible (< 50 à 100 mA selon modèles). Vérifier le modèle disponible ; solution de repli : alimenter le Nano par une prise USB du PC ou de l'AD3, ou ajouter une charge factice.
  6. Mesure au shunt : ne pas alimenter en même temps par le PC et la Powerbank. Pointes AD3 : 1− n'est pas à la masse (mesure différentielle) ; si l'AD3 indique du bruit, utiliser la fonction de moyenne (Average) et le mode de déclenchement Single.

Corrigé Partie 0 : Pourquoi LoRa ?

✅ Corrigé Q0.1 & Q0.2
  • Q0.1 — Critères attendus (3 au choix, chiffrés) : portée 2–5 km (ville) à 10–15 km (rural) contre 30–100 m pour Wi-Fi et 10–100 m pour BLE ; consommation / autonomie : mois à années sur pile (veille de quelques µA) contre heures/jours en Wi-Fi (100–300 mA) ; coût d'usage : pas d'abonnement (réseau privé) contre SIM + abonnement en 4G ; bande 868 MHz libre et mieux pénétrante dans les murs ; une passerelle pour tout le campus (topologie en étoile). Inconvénient : faible débit (0,3–5,5 kbit/s) et messages courts (51–222 octets), duty cycle ≤ 1 %, latence (Classe A).
  • Q0.2 — Durée ≈ × 25,6 (1 319 ms / 51,5 ms) ; gain de sensibilité 14 dB (−123 → −137 dBm) ; énergie par trame ≈ × 25 (même courant, durée 25 fois plus longue) donc batterie épuisée plus vite ; intervalle mini passe de 5,2 s à 132 s (1 % de duty cycle) : on gagne en portée mais on perd en débit et en fréquence d'émission. Règle pratique : choisir le plus petit SF qui assure une marge de liaison suffisante (c'est le principe de l'ADR).

  • Q1.1 — Non : la passerelle ne déchiffre rien (chiffrement AES-128 entre le nœud et le serveur) ; elle recopie la trame radio dans un paquet IP sans l'interpréter : elle est « transparente ».
  • Q1.2 — UDP : liaison sans connexion, légère, adaptée à un flux régulier de petits paquets (pas de poignée de main TCP à chaque trame) ; la fiabilité est assurée plus haut dans le protocole LoRaWAN (compteur de trames). La passerelle ajoute : RSSI, SNR, horodatage, fréquence, SF/DR, identifiant de la passerelle.
  • Q1.3 — (1) Alimentation / LED SYS et liaison réseau (câble, IP) ; (2) paramètres du transfert : adresse du serveur, port UDP 1700, Gateway ID identique à celui déclaré dans ChirpStack ; (3) côté serveur : services ChirpStack / gateway-bridge démarrés, pare-feu laissant passer 1700/udp.

  • Q2.1 — Le DevEUI (64 bits) est l'identifiant unique de l'équipement ; le serveur s'en sert pour reconnaître le nœud lors du join, retrouver sa clé (AppKey) et lui associer ses données.
  • T3 (valeurs typiques) : join en ≈ 5 à 8 s (la réponse du réseau est émise 5 s après la demande, fenêtre RX1/RX2) ; 1re trame ex. data = APUTigc= ↔ 00 F5 13 8A 07 ; fréquence parmi 868,1 / 868,3 / 868,5 MHz (saut de canal à chaque trame) ; SF7 / DR5 ; RSSI de −50 à −90 dBm, SNR de +8 à +12 dB en salle.
  • Q2.2 — 00F5 = 245 → 24,5 °C ; 138A = 19 × 256 + 138 = 5 002 mV (≈ 5,0 V) ; 07 = trame n° 7. Bonus : FFEC = 65 516 non signé = −20 en complément à 2 → −2,0 °C.
  • Q2.3 — 5 octets contre 11 caractères : trame radio plus courte (18 octets contre 24 sur le canal), donc durée d'émission réduite d'environ 17 % en SF7 (51,5 ms contre ≈ 61,7 ms) et davantage en SF élevé ; moins d'énergie, moins de duty cycle consommé, plus de marge pour émettre souvent. Le décodage est fait côté serveur / supervision.

  • Remarque métrologie : avec le shunt de 1,1 Ω, I = U / 1,1 ; un courant de 100 mA donne 110 mV. Les deux fenêtres RX1 (+1 s) et RX2 (+2 s) apparaissent comme de petits paliers de quelques mA après l'émission (classe A).
  • Q4.1 — Résolution de lecture des curseurs (largeur de trait, quelques ms), tolérance de la résistance (±5 % sur 1,1 Ω → ±5 % sur I), bruit de mesure et résolution verticale de l'AD3 (20 mV/div), horloge du modem et temps de commutation avant/après l'émission.
  • Q4.2 — Exemple : C = 5 000 mAh, Iveille = 30 mA, ITX = 90 mA. SF7 : Imoy = 30 + 60 × 0,0515/60 ≈ 30,05 mA → autonomie 0,7 × 5000 / 30,05 ≈ 116 h ≈ 4,9 jours. SF12 : Imoy = 30 + 60 × 1,319/60 ≈ 31,3 mA → ≈ 112 h. La radio représente moins de 5 % du courant moyen : la consommation est dominée par le Nano et le modem laissés actifs en permanence (Iveille). Solution : mise en veille profonde (PWR_DOWN + réveil par Watchdog, déjà vu au TP « Autonomie ») et mise en veille du modem (AT+LOWPOWER) : courant moyen de l'ordre de quelques centaines de µA, soit plusieurs mois voire années. Énergie d'une trame SF7 : 5 V × 90 mA × 51,5 ms ≈ 23 mJ seulement.
  • Q4.3 — Avantages : portée (liaison encore fiable avec marge positive au point C, là où le Wi-Fi n'accroche pas) ; faible énergie par trame (quelques dizaines de mJ) ; une seule passerelle pour tout le campus, sans abonnement ; installation simple (OTAA, aucune configuration réseau côté nœud) ; chiffrement intégré. Limites : débit et taille de trame (5 octets utiles ici), duty cycle (SF12 ≈ 1,3 s par trame), latence (classe A : le nœud n'écoute qu'après émission), dépendance à la passerelle/serveur. Pour une image toutes les 10 s : Wi-Fi (ou 4G si hors portée) car LoRaWAN est inadapté aux gros volumes de données.

📎 Annexe A — Variante The Things Network (TTN) au lieu de ChirpStack
  • Passerelle : même mode Semtech UDP, serveur eu1.cloud.thethings.network, ports 1700 ; déclarer la passerelle (Gateway EUI) dans la console TTN, créer une application et les équipements (DevEUI, JoinEUI, AppKey, plan EU868, LoRaWAN 1.0.3).
  • Node-RED : s'abonner au broker TTN (eu1.cloud.thethings.network:1883, identifiant = application-id@ttn, mot de passe = clé API) sur le sujet v3/+/devices/+/up. Adapter le nœud de décodage :
const m = msg.payload;
const b = Buffer.from(m.uplink_message.frm_payload, 'base64');
const rx = m.uplink_message.rx_metadata[0];
const sf = m.uplink_message.settings.data_rate.lora.spreading_factor;
// puis : temperature = b.readInt16BE(0)/10 ; rssi = rx.rssi ; snr = rx.snr ; device = m.end_device_ids.device_id
📎 Annexe B — Pistes d'extension (élèves en avance)
  • Passer en AT+ADR=ON et observer le SF choisi par le réseau en fonction de la qualité de la liaison.
  • Ajouter un décodeur JavaScript dans ChirpStack (Device profile → Codec) pour faire apparaître object.temperature dans les événements.
  • Mise en veille du Nano (PWR_DOWN + Watchdog) et du modem (AT+LOWPOWER) puis nouvelle mesure de Iveille à l'AD3.
  • Envoi d'une alarme (unconfirmed → AT+CMSGHEX confirmé) lorsque la température franchit un seuil, et comparaison de la consommation.
